Which server should edit images and run prompt enhance?

IncreArt can drive image editing through sd-server or KoboldCpp, on ROCm or Vulkan, with flash attention and CPU offload on or off. This compares every single-GPU combination on one real job: a 1 megapixel Qwen-Image 2.1 edit with one reference image, plus prompt enhance (PE) with Qwen3-VL 8B on the GPU and on the CPU.

2× Radeon AI PRO R9700 32 GBi9-14900K · 188 GB RAMROCm 7.2.4 · Mesa 25.0.7 RADVLinux 6.17

Recommendations

  1. Edit images with sd-server on ROCm with flash attention. It is the fastest setup: 102 s per image once the prompt is encoded (126 s for a new prompt) at 25.6 GiB of VRAM.
  2. Add CPU offload when the card must hold something else. Offload costs only 4% (105 s per image) and cuts VRAM to 4.5 GiB, using 17.3 GiB of RAM instead.
  3. Keep PE off the card that edits images. Sharing one card, images slowed by 41% (146 s each) and PE fell from 58 to about 2.6 tokens/s, because together they overflow 32 GiB and part of their memory moves to system RAM. Put PE on the other card. If both must share one, the offload setup above should leave room (not measured).
  4. Run PE on a GPU. Answers take 2.0–2.9 s on a GPU against 5.5–80.7 s on the CPU, for 7.2 GiB of VRAM.
  5. Use KoboldCpp only with GGUF files and the text encoder on the GPU. Set up as in its official Qwen-Image 2.1 template, it takes 201 s per image (2.0× sd-server on ROCm) in 14.5 GiB of VRAM. Its default puts the text encoder on the CPU, and the int8 files expand to 29 GiB and fail.
  6. Avoid the rest. Without flash attention ROCm is 3.5× slower; sd-server on Vulkan is 4.7× slower, and about 50 minutes per image without flash attention.

PE and image editing on one card

sd-server (ROCm, flash attention) and the PE server loaded together on card1, with PE answering one request after another for the whole 20 minutes of image generation (29 answers). This is the worst case: in the app PE runs only when asked.

  • The first two images took 190 s and 270 s; after that each took 146 s, against 103.2 s on the same card alone.
  • PE generated 58 tokens/s at first and about 2.6 tokens/s by the end. After the images stopped it ran at 8 tokens/s, because its memory had been moved to system RAM and stayed there.
  • Together they peaked at 29.8 GiB of VRAM plus 4.1 GiB placed in system memory.

Loading

sd-server loads the model on the first request, so load time shows up in the warm-up (one 512 px step).

  • The first case of the day took 222 s on ROCm, reading about 17 GB of models from disk. Later ROCm cases took 9–27 s and Vulkan 11 s, with the files in the page cache.
  • KoboldCpp loaded the GGUF files in about 13 s. With the int8 files it took 2.8 minutes, converting every tensor.
  • These are indicative only. Another program on this machine (increbot) frees and refills RAM in response to memory use, which decides whether model files are still cached.

Method

  • Job. Qwen-Image 2.1 int8 (diffusion model 7.3 GB, Qwen3-VL 8B int8 text encoder 9.4 GB, bf16 VAE), euler, 20 steps, CFG 2, 1024×1024, one 1024×1024 reference, an edit prompt turning a scene to winter. Seeds 1, 2, 3… so every image is new work.
  • Repeats. At least three repeat images, more if they differed by over 3%. Setups taking minutes per image timed one repeat after the new-prompt image; repeats varied by under 1.5% everywhere they were measured more than once.
  • Two cards at once. Cases ran in two lanes, one per card. ROCm with flash attention ran on both as a control: 103.2 s on card1 and 100.2 s on card2, 3% apart, with identical memory.
  • Memory. Sampled every 100 ms. VRAM is the rise in the card's used memory where the card had no other user, and the server's own allocations (/proc/<pid>/fdinfo) on card2, which another program also used. With offload on ROCm, the per-process count includes host memory mapped for the card (17.3 GiB), so the card's rise is the true figure. On Vulkan the per-process count read 1.9 GiB below the card's rise on the idle card, so card2's Vulkan figures are likely a little low.
  • Stopped early. Vulkan without flash attention needed ~150 s per step and was stopped. KoboldCpp was first run with the int8 files and its default CPU text encoder; that looked CPU-bound and was stopped, then rerun as described above.
  • KoboldCpp runs. Done after the main run, with nothing else on either card: the template's files (leejet's Qwen-Image 2.1 GGUF, Qwen3-VL 8B Q4_K_M with its F16 mmproj as --sdclip1, --sdclipdevice main). Its images are as good, but differ from sd-server's for the same seed.
